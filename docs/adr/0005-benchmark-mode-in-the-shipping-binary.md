# Benchmark Mode lives in the shipping binary

Performance work targets the Vita, on the device and in Vita3K, where there is no profiler we can script and no command line. So benchmarks run inside the normal VitaDeck build: a `bench/request` file in the VitaDeck Data Root turns on Benchmark Mode for one launch (`src/core/bench.c`). It plays scripted pad input against installed example Deck Apps, keeps timings in preallocated memory, writes `bench/result.json` once at the end, and exits. `scripts/bench.sh` places the request and collects the result: a file on the host and in Vita3K, VitaShell FTP on the device.

Measuring the binary that ships keeps the numbers honest. Off, each hook is a call that returns on its first branch, so normal runs pay nothing measurable. On, a frame costs about ten monotonic clock reads, a JS loop iteration about six, and there is no I/O or logging until the run ends. Per-thread CPU time comes from the OS (`runClocks` on the Vita) and is read twice per scenario.

**Considered options:** a separate benchmark build with a compile-time flag (rejected: a second VPK to build and upload, and it measures a different binary); a CTest harness like the smoke test (rejected: it only runs on the host, and host numbers say little about the Vita); per-frame logging through `TraceLog` (rejected: logging on the Vita is slow enough to skew what it measures); sampling profilers (none for the Vita that we can drive from a script).

**Consequences:** scenarios and their input scripts are C (`SCENARIOS` in `src/core/bench.c`) and drive the example Deck Apps, so changing an example can change a benchmark. Re-record the baseline (`scripts/bench.sh <target> --update-baseline`) when that happens. Vita3K numbers reflect the emulator on the machine that ran it; compare them only against a baseline from the same machine, and treat the device as the source of truth.
